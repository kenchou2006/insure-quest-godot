# RAG 計畫：法規 ＋ 法巴人壽公開商品條款（草案，2026-10-23）

> 狀態：調查完成，待團隊決定（見 §6）後再交 agy 實作。標「⚠️」者為尚未查證、需人工確認。

## 1. 目的與原則

- 讓合規判斷與 AI 培訓報告「附上依據」：引用內容來自檢索到的原文（法規條文、商品條款），不是模型記憶，解決目前「只敢寫法規名稱、不敢寫條號」的限制。
- 簡報 03 應用技術章可如實寫「RAG 文件檢索」；04 章可回答「換成公司自己的規範／商品，只要換知識庫」。
- **護欄不變**：分數、評等、結局、金額仍只由規則引擎決定；RAG 只產生「依據」與說明文字。保障卡仍是功能概念，真實商品只做「對照與揭露練習」，不做推薦。

## 2. 查到的公開資料（法巴人壽台灣官網 life.cardif.com.tw）

- 商品依類別分頁：投資型（/a211）、保障型人壽（/a231）、傷害（/a232）、健康（/a233）、信用保障（/a251）、分紅（/ntd-participating-insurance）。頁面**沒有標示現售／停售** ⚠️。
- 每張商品有「保單條款」PDF（`/documents/.../VIE_<代碼>.pdf`），部分有「瞭解更多」DM；投資型另有商品說明書（`Vie_SPM_<代碼>.pdf`）。
- 公開資訊 /a5「商品總覽」有 13 份彙整 PDF，其中「1、商品名稱與核准、核備或備查日期及文號」可用來標注版本日期，「2-2 承保範圍及不保事項－不保事項」正好是揭露練習素材。
- **條款 PDF 可直接抽文字**：實測「活力成家定期壽險」條款（VIE_XCSAG.pdf）8 頁、約 2.7 萬字、29 條；開頭「內容摘要」把主題對到條號（例：除外責任及受益權之喪失→第 17、18 條；契約撤銷權→第 3 條），適合「一條一段」切塊。
- 2026 公司商品主軸（經濟日報 2026 報導）：投資型保單、分紅保單、房貸壽險。

## 5. 技術設計（單一 Worker，不新增部署）

- **切塊**：一條一段；metadata = `{source: 'law'|'product', doc, article, title, url, version_date}`。商品條款優先收「契約撤銷權、保險範圍／給付、除外責任、告知義務」等條。
- **嵌入與索引**：Workers AI `@cf/baai/bge-m3`（多語、官方目錄有此模型）＋ Cloudflare Vectorize。⚠️ 輸出維度（模型卡為 1024）與 Vectorize 本機開發支援需實測；Workers AI 本機需連遠端（專案已有 `npm run dev:remote-ai`）。
- **建庫**：離線腳本（`server/tools/`）抽 PDF 文字 → 切塊 → 呼叫嵌入 → 寫入 Vectorize；切塊結果另存 JSON 進版控，方便人工核對與重建。
- **查詢點**：
  1. 合規掃描／合規雷達：違規語句 → 取 top-2 法規條文 → 結果卡顯示「依據：〈法規〉第 N 條＋摘錄＋連結」。
  2. 方案配置：選定保障卡 → 顯示對應公開商品的「應主動告知」2–3 條（承保範圍、除外責任、契約撤銷）＋「教學用途，以官方最新條款為準（擷取日期）」。
  3. AI 培訓報告：教練回饋 prompt 帶入檢索片段，要求引用（片段以不可信資料包裝，沿用現有 prompt-injection 防護）。
- **退回機制**：訪客模式在瀏覽器跑（`local-room.js`），沒有後端可檢索 → 用切塊 JSON 產生的靜態「違規類型 → 條文」「保障卡 → 商品重點」對照表。Vectorize 失敗時同樣退回。
- **工作量估計**：程式 2–3 天＋資料整理核對 1–2 天（需團隊成員）。

## 6. 需要團隊決定的事

1. **是否在遊戲中使用法巴真實商品名稱與條款**：⚠️ 請先查競賽辦法（官網 PDF）對使用主辦方品牌、商品資料的規定。若有疑慮，可改為「商品類型＋條款摘錄，不顯示商品名」。
2. 是否同意 README／簡報中「保障卡不對應任何真實商品」的說法改為「保障卡為功能概念；另提供公開商品條款對照，僅供揭露練習」。
3. 誰負責逐條核對知識庫內容（法規＋5 張商品）。
